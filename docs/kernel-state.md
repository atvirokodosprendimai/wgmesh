# Kernel state: how the daemon writes the kernel

Decision record: [ADR-0003](adr/ADR-0003-kernel-state-apply/ADR-0003-kernel-state-apply.md). This page is for the operator of a mesh and is the release note for the releases that bring it in. The release after the first is a row in [the backlog](adr/BACKLOG.md), not a task.

Every tick the daemon reads what the kernel holds, computes one desired state from the active peers, and writes only the difference. No byte on the wire changes, no flag or file changes shape, so old and new nodes talk to each other during the whole rollout.

## The converge step, once per tick (every 5 seconds and on SIGHUP)

1. **Observe.** One `wg show <iface> dump` (peers, endpoints, AllowedIPs, handshakes); the routes of the mesh interface for both families (`ip route show dev <iface>` and `ip -6 route show dev <iface>`; `netstat -rn -f inet|inet6` on macOS); `ip -o addr show dev <iface>`; and, on Linux when forwarding is wanted, `/proc/sys/net/ipv4/ip_forward` and `iptables -C FORWARD -i <iface> -o <iface> -j ACCEPT`.
2. **Desire.** One desired state: every peer's AllowedIPs and every route come from the same owner choice, so a route to a network no peer may carry cannot exist.
3. **Plan, apply.** Per target the difference only, one item at a time; a failed item never skips the others. Removals run before adds for addresses; peers that shrink are set before peers that grow, so a moved network is never held by two peers.
4. **Result.** One result per item. A result is logged when it differs from the last one of that item: a failure once, a recovery once (`<op> <target> <key>... done` for a write, `... recovered` after a failure). A steady node with nothing to correct writes nothing and logs nothing; a standing warning case (a stale address, a forced forward on a node that does not need it) is logged once and counted once, not on every tick.
5. **Relay probe (ADR-0004).** With the relay-probe switch of ADR-0004 on, a relayed peer that has a usable endpoint stays configured with its endpoint and no AllowedIPs (written as the explicit clear), so a fresh handshake can bring it back; a peer that also relays for another peer keeps its routes. The relay plan is stored before the apply, and an unreadable kernel skips the tick before anything is stored.

A target that cannot be read is skipped for that tick and never read as empty. A failed or unparsable `wg show dump` skips the whole converge step: no peer, route, address or forwarding change from it, and the relay table is not updated (one line, `Cannot read the WireGuard interface, skipping this tick`, then `Reading the WireGuard interface works again`). Collision resolution (`collision.go`) runs after it in the same reconcile and is not skipped: a node that loses an IP collision still flushes the address family of its interface and sets the new address (see Release switches, Addresses).

## One owner for a shared network

When several peers advertise one network, the node picks one owner:

1. A peer with a handshake newer than `HandshakeStaleAfter` (150 s) beats one without.
2. Among fresh peers the owner read back from the kernel keeps the network (no automatic fail-back).
3. Otherwise the lowest mesh IP wins, compared as a number (`10.99.0.9` before `10.99.0.10`), then the lowest public key.

- The choice is per node: two nodes may pick different owners, because it only decides this node's outbound traffic.
- Failover bound: the network moves at the first tick after the owner's last handshake is `HandshakeStaleAfter` old, so at most `HandshakeStaleAfter` plus one `ReconcileInterval` (5 s) after that handshake. This is read from the constants (`pkg/daemon/daemon.go`), not measured.
- A network this node advertises itself is owned by nobody: two HA exit nodes each drop the other's default route (`routes.ExcludeOwn`, unchanged).
- Limit: when the owner is relayed, the kernel holds the network under the relay's key, so the "observed owner stays" step never matches and the lowest-IP rule decides. The owner is still one and stable, but it does not stay on a fresh peer that is not the lowest (BACKLOG).
- The owner that lost is logged once per change: `Shared network <net>: owner <key> via <gw>, ignored <key> via <gw>`.

## Release switches

Four switches exist (`EnforceForwardScope`, `EnforceRouteGuard`, `EnforceAddressRemoval`, `EnforceRevertOnExit`) and are `false` in release N. Flip one only when every node runs the release before it. A switch is an exported Go `atomic.Bool` package variable compiled into the binary (`pkg/daemon/converge.go`): there is no flag, file, signal or reload that changes it on a running node; only a new build with the line changed does.

| Switch (rule) | At N | At N+1 | Counter to read before flipping |
|---|---|---|---|
| `EnforceForwardScope` (`forward-scope`) | every Linux node still gets `ip_forward=1` and the FORWARD rule; one line and one count when the node neither is an introducer nor has `advertise-routes` | only an introducer or a node with `advertise-routes` is forced; others are left alone | `wgmesh_kernel_warnings_total{rule="forward-scope"}` zero, or every node that counts it should forward (set `--introducer` or `advertise-routes`) |
| `EnforceRouteGuard` (`attached-network`) | a peer's route to a network this host is attached to (equal or inside) is still installed; one line and one count | the route is left out of the routes and the AllowedIPs; the line is logged, the Linux counter no longer counts | `{rule="attached-network"}` zero |
| `EnforceAddressRemoval` (`stale-address`) | an address on the mesh interface inside the mesh network that is not this node's is warned about, once per address while it holds, and kept | it is removed (`removing <addr>: inside the mesh network and not this node's address`) | `{rule="stale-address"}` zero |
| `EnforceRevertOnExit` | a graceful exit logs one line naming what this run added or changed (`revert-on-exit: this run added the FORWARD rule on <iface> and changed ip_forward from 0 to 1; it stays after exit, ...`) and runs no command | the exit deletes the FORWARD rule this run appended and sets `ip_forward` back to 0 if this run changed it from 0 and it still reads 1 (`delete forward FORWARD... done`, `restore forward ip_forward... done`) | no warnings counter: `wgmesh_kernel_warnings_total` has no series for it. A successful delete or restore at N+1 is counted in `wgmesh_kernel_changes_total{target="forward"}` (the metric has no op label; the log line says delete or restore), so a rise of that counter at exit is the revert. At N the N line shows which nodes will undo something, and a node whose other services need forwarding across a restart should not be flipped |

- `attached-network` on macOS is enforced from the first release, whatever `EnforceRouteGuard` says (there was no old behaviour), and is counted there.
- `ip route replace` of an attached network overwrites the host's own connected route for it (reproduced on the maintainer's Linux laptop, kernel 6.17.0-41, iproute2 as installed there, in a throwaway network namespace, 2026-11-16: `192.168.50.0/24 dev dum0 proto kernel` was replaced). The daemon restores the connected route when it later removes the route. A supernet of an attached network is kept; the mesh subnet, the mesh IPv6 prefix and link-local networks are never counted as attached.
- Addresses: the address target adds a missing mesh address and, at N+1, removes a held address inside the mesh network that is not this node's (an address an operator added by hand there included); the address target itself never flushes. A point-to-point address (`inet A peer B`) is never touched. Flushes happen elsewhere: `setInterfaceAddress` (`pkg/daemon/helpers.go`) runs `ip -4|-6 addr flush dev <iface>` for the family of the address it sets, once for each family at daemon start and again for IPv4 whenever this node loses an IP collision (`collision.go` calls it through `applyInterfaceAddress`), so every address of that family on the mesh interface, a hand-added one included, is lost then and the node's own is added back; `resetInterface` flushes all addresses when the interface already exists at daemon start.
- An IPv6 address is held once whatever its prefix length: the kernel refuses `ip -6 addr add fd99::1/128` while `fd99::1/64` is held (`Error: ipv6: address already assigned.`, not `File exists`; reproduced on the same laptop and namespace, 2026-11-16). So at N an IPv6 address held with another prefix length than the one wanted is not added (the add could never succeed) and is warned about once as `stale-address`; at N+1 the plan removes the held one first and then adds the wanted one. The daemon also counts that error text as success for an add.

## Reading the counters

Both need `--metrics` (see the README, Metrics): enable it on every node and check that each answers before reading a zero.

How to check one node: `curl -s <addr>/metrics | grep wgmesh_kernel`, where `<addr>` is `http://<host>:<port>` of the `--metrics` value given to `wgmesh join` (`--metrics :9090` is `http://<host>:9090/metrics`, README, Metrics). A healthy scrape of a settled node shows `wgmesh_kernel_changes_total{target="peer"}` (present from start, one count per peer after a start) with the same value on two scrapes a minute apart, no `{target="route"}`, `{target="address"}` or `{target="forward"}` line beyond the first writes after start, and no `wgmesh_kernel_warnings_total` line, or only for cases you know about. An empty reply or a refused connection is not a zero: the node has no `--metrics`.

- `wgmesh_kernel_changes_total{target}`: writes that changed the kernel. `target` is `peer`, `forward`, `route` or `address`. In a steady state it is flat; a restart adds one `peer` count per peer, because the pushed endpoints are memory only and every peer's endpoint is pushed once.
- `wgmesh_kernel_warnings_total{rule}`: `rule` is `forward-scope`, `host-default`, `attached-network`, `foreign-route` (macOS) or `stale-address`. A case is counted once when it starts and again only after it stopped and returned, not on every tick. Only `peer` of the changes counter exists at start; every warning series is absent until counted, so write an alert as `sum by (rule) (wgmesh_kernel_warnings_total) or vector(0)`. Counters reset on restart: the gate is "zero since process start on every node".

## Default route

An advertised `0.0.0.0/0` (or `::/0`) is installed with `ip route replace`: it is a feature. The route key is the destination and metric, not the device, so it **replaces** the host's own default route of that family when that one has the metric the mesh route gets (0 for IPv4, 1024 for IPv6); the host's one is not kept next to it (reproduced on the maintainer's Linux laptop, kernel 6.17.0-41, iproute2 as installed there, in a throwaway network namespace, 2026-11-16: `default via 10.0.0.1 dev dum0` was gone afterwards). When the host already has a default route of that family on another device, one line and one count say so (`host-default: this host already has an IPv4 default route on <dev>; the mesh's IPv4 default route on <iface> replaces it ...`). A host default of another metric (a DHCP `metric 100`) is not replaced: the mesh default is added next to it and the lower metric wins (the mesh route has 0 for IPv4 and 1024 for IPv6, so an IPv6 host default below 1024 keeps winning), the line says `... (metric 100); ... the lower metric wins, and the host's stays`, and nothing is remembered or restored for it. For a replaced one the daemon remembers the host default route (device, gateway, metric and `onlink`, in memory; not `proto`, `src` or `expires`) and puts it back once with `ip [-6] route replace default [via <gw>] dev <dev> [onlink] metric <m>` when the mesh default route of that family is removed (its peer is gone) or at a graceful exit, before the interface is deleted (deleting it drops the mesh default with it; this restore is not behind `EnforceRevertOnExit`): one line (`host-default: restored the host's IPv4 default route via "<gw>" dev <dev> metric 0 after the mesh default route was removed`, or `... at exit, before <iface> is deleted`), one count in `wgmesh_kernel_changes_total{target="route"}`, and the record is forgotten. Before restoring, the daemon reads the host's default routes again: when one of the recorded metric is back on a device other than the mesh interface (an IPv6 router advertisement, a DHCP renewal), it restores nothing and logs `host-default: the host has its ... default route again`. (A failed restore is logged as `Failed to replace route default (host) d...: failed to restore the host default route dev <dev>: ...` and not retried). The record is not kept across a restart and is taken only from a read made while the mesh default was not installed, so a daemon that starts with the mesh default already installed has nothing to restore, and a crash or `SIGKILL` restores nothing: put the host default back by hand.

Caveat, not built and not run (BACKLOG): the node's own WireGuard UDP traffic may be routed into the mesh interface once a default route is accepted. A transport exemption (an `fwmark` on the socket and a policy rule) is a separate decision.

## IPv6 and macOS

- An IPv6 route uses the carrier's mesh IPv6 as gateway: the relay's when the peer is relayed, falling back to the peer's own when the relay has none (`pkg/daemon/desired.go`, `gateway6`). `ip` refuses an IPv4 gateway for an IPv6 network (reproduced on the maintainer's Linux laptop, kernel 6.17.0-41, in a throwaway network namespace, 2026-11-16). A network whose carrier and peer both have no mesh IPv6 is skipped (one line); with `--no-ipv6` IPv6 networks are not routed (one line per network).
- IPv6 routes on the mesh interface are now managed: a route `ip -6 route ... via` that an operator added on it is removed when it is not desired. Before, only IPv4 was read.
- macOS routes (`route -n add|change|delete [-inet6] -net <cidr> -interface <utun>`, no gateway; `-inet6` is added for an IPv6 network) are built and tested against hand-written fixtures only. **They are not verified on a real Mac: the T6 sign-off is open.** Every format assumption (the `netstat` columns, taken from the header; a `link#N` gateway or the interface name; the flags) is written from the man page and is unverified.
- From release N a Mac gets route writes for the first time: the old code did nothing on macOS. No release switch holds them back (`EnforceRouteGuard` is ignored there), so a Mac operator who sees a wrong route rolls back by installing the previous binary; the daemon recreates the interface at every start, and the routes of the new release are not kept.
- macOS deletes only routes this daemon run installed (an in-memory set; the interface is recreated at every start), so a route left by hand or by an earlier run stays.
- macOS rule `foreign-route`: a peer's network that another interface already routes (the Mac's own default via `en0`, another VPN) is not re-pointed into the mesh; it is skipped, logged once and counted. A mesh-interface row the parser does not know is logged once (`unrecognised route row`).
- `EnforceRouteGuard` is ignored on macOS: attached networks are always dropped there. Forwarding is not configured on macOS.

## Log lines

These texts are gone: `Failed to configure peer <key>: ...`, `Failed to remove obsolete peer <key>...: ...`, `Failed to sync peer routes: ...` and `Failed to install relay FORWARD rule for <iface>: ...`. An alert or a log grep that matches one of them stops matching without an error: search your alert rules for those four texts and replace them.

The new texts are `Failed to <op> <target> <key>...: <error>` once per change of the error, then `<op> <target> <key>... recovered`. Grep for `Failed to set peer`, `Failed to remove peer`, `Failed to del route`, `Failed to replace route` (macOS: `Failed to add route`, `Failed to delete route`, `Failed to change route`), `Failed to add address`, `Failed to del address`, `Failed to set forward` and `Failed to append forward`. The key in the prefix is cut to 16 characters (`shortKey`). A route failure carries the whole network and gateway in its error text (`failed to add route <net> via <gw>: ...`); an address or forwarding failure carries only the command's output, so the cut key is all the prefix shows of the address.

The once-only lines: `forward-scope:`, `revert-on-exit:` (at N, once per exit, only when this run added the rule or changed ip_forward), `host-default:` (the warning and `restored the host's`), `attached-network:`, `foreign-route:`, `stale address`, `removing <addr>: inside the mesh network ...` (N+1: printed on every attempt), `Cannot read the ... skipping`, `Reading the ... works again`, and `iptables not found: the FORWARD rule for <iface> is not managed on this node` (when `iptables` is missing). Stale cleanup and eviction still log `[Peers] Failed to remove stale peer` and `[Health] Failed to remove evicted peer`.

## Known limits

- A forced reconnect never touches a relayed peer (its networks sit under the relay): `[Health] Peer ... has no WireGuard peer entry of its own`.
- `reconcile` is serialised; health writes (reconnect, eviction, stale cleanup) take the same converge lock, so a tick and a health write never interleave.
- A peer removed by stale cleanup is added again on the first tick after it returns (the old code kept it out of the kernel until its configuration string changed).
- When the desired peer set is empty and the kernel still holds peers (a momentarily empty peer store), the plan removes every kernel peer (`planKernel`); skipping removal in that case is a BACKLOG row.
- The `wg` forks have no deadline. A hung `wg` also holds the converge lock and so blocks eviction. A deadline belongs to ADR-0007 (not in this tree).
- A graceful exit (`SIGINT`, `SIGTERM` or a daemon `Shutdown`, in `wgmesh join`) undoes forwarding only after the background goroutines have stopped and before the interface is deleted, and only what this run did: the FORWARD rule when `iptables -C` found it absent at the first tick that read it and the `-A` succeeded, `ip_forward` when this run read 0 and wrote 1. A rule or a value found in place is never touched, also when someone removed it and a later tick wrote it again. Order: the rule, then the sysctl. A failed `-D` or `sysctl` is logged (`Failed to delete forward FORWARD...`, `Failed to restore forward ip_forward...`) and not retried. A crash or `SIGKILL` leaves the host as before, and a restart (an upgrade, `Restart=always`) opens a gap in which other services on the host get no forwarding. Routes and addresses are not reverted: deleting the interface removes them. The exception is a host default route the mesh default replaced: it is put back before the interface is deleted, whatever `EnforceRevertOnExit` says (see Default route).
- Shared host (two daemons, `wg0` and `wg1`, or any other user of the global `ip_forward`): the exit reads `/proc/sys/net/ipv4/ip_forward` again and restores 0 only if it still reads 1; a read error or another value is skipped and logged once (`revert-on-exit: ip_forward is not restored: ...`). A daemon that wrote 1 and a second daemon that read 1 and relies on it: the first one's exit still restores 0, and the second loses forwarding until its next tick (at most 5 s) writes 1 again. A service that started after us and found `ip_forward=1`, and reads it once, is not healed. Not fixed; the fix needs a count of users outside this process.
- A claim is not atomic: between our observe (`iptables -C`, the `ip_forward` read) and our write another process may set the value or add the rule; our write then succeeds, we then claim it as ours, and the exit undoes what that other process wanted.
- On a plain stop (no restart) the restore is permanent for any service that started after us and found `ip_forward=1` without setting it: it keeps running with forwarding off after we exit, and nothing writes 1 again.
- A second `SIGINT` or `SIGTERM` during shutdown is swallowed (`signal.Notify` stays active and nobody reads it). If a hung `wg` fork holds the converge lock, the exit waits for it and only `SIGKILL` ends the process, which skips the revert.
- A panic skips the revert and the interface teardown (unchanged), so the host stays as after a crash.
- Real `netstat` output on a Mac has not been recorded (BACKLOG).

## Mixed fleet

Each node chooses its own owner and writes only its own kernel, so a node with this change and a node without it interoperate. Flip a switch only when every node runs the release before it: a node that forwarded for no reason is the one an N+1 node stops.

## Rollback

All kernel state is runtime state. Reverting from N to the old release restores the old tick, which re-applies everything blindly; the kernel left by N is the kernel the old daemon leaves. After N+1 a rollback to N's binary restores nothing that N+1 changed: an address removed at N+1 (an operator's address inside the mesh network included) stays gone, and N does not add it back; put it back by hand. A route that N had installed to an attached network and N+1 removed is installed again by N, which again overwrites the host's connected route for it. Setting the switches back to `false` is a later release, not a rollback, and it undoes no earlier removal. A rollback to a binary without the exit revert (T8, built; on at N+1) only re-introduces the #872 leak (`ip_forward` and the FORWARD rule left behind at exit), and nothing else.
